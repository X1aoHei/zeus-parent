# ADR-0001: 导出任务执行架构：MQ 优先 + 定时任务兜底

## 状态

已接受

## 背景

导出模块需要支持异步任务执行。最初采用 xxl-job 定时轮询模式，但存在以下问题：

1. **实时性差**：轮询间隔导致任务不能及时执行
2. **资源浪费**：无任务时定时任务仍在运行

需要引入 MQ 消息驱动，同时保留定时任务作为兜底机制。

## 决策

### 执行架构

采用 **MQ 优先执行 + xxl-job 定时兜底** 的双保险模式：

```
提交任务 → 创建 DB 记录（Pending）→ 发送 MQ 消息
                                          ↓
                                    MQ 消费者直接执行
                                          ↓
                                    （失败时）xxl-job 轮询 Pending 任务兜底执行
```

### 互斥机制

MQ 消费者和定时任务可能同时处理同一个任务，需要互斥保护。采用 **Redis 分布式锁 + 乐观锁** 双重互斥：

1. **第一道：Redis 分布式锁** — 快速失败，避免不必要的 DB 操作
2. **第二道：乐观锁（version 字段）** — 数据库层面兜底，`UPDATE ... WHERE version = ?`

### 幂等机制

用户可能重复提交导出请求，需要幂等保护。采用 **Redis SETNX + 数据库唯一索引** 双重幂等：

1. **Redis SETNX** — 快速拦截，300 秒过期
2. **数据库查询兜底** — 防止 Redis 失效时的穿透

### 消息体设计

MQ 消息体只传 `taskId`，消费者查库获取完整信息。理由：

1. 消息体轻量，减少 MQ 存储压力
2. 保证数据一致性（以 DB 为准）
3. 任务参数可能较大，不适合放在消息体中

## 备选方案

### 1. 纯轮询模式
- 优点：简单
- 缺点：实时性差，资源浪费

### 2. 纯 MQ 模式
- 优点：实时性好
- 缺点：MQ 故障时任务丢失，无兜底

### 3. 数据库行锁互斥
- 优点：实现简单
- 缺点：性能差，锁持有时间长

## 影响

- 新增 `zeus-mq` 模块依赖
- 新增 `zeus-redis` 模块依赖
- `ExcelExportTaskEntity` 新增 `version` 字段（需 DDL 变更）
- `ExcelFeignHandler` 接口签名变更（接收实体对象而非分离参数）
